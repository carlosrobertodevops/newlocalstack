#1 · routing

Make cloud routing data-driven

Strong

Files

  • aws/handlers/multi_cloud.py (~233 LOC, god-handler)
  • cloud/base.py CloudProvider.edge_hosts
  • cloud/builtin.py edge_hosts metadata (source of truth)
  • cloud/edge.py already data-driven fnmatch

Problem

Routing knowledge lives in three places. multi_cloud.py hardcodes every Azure/GCP host suffix + path prefix inline (lines 21–96) and ignores CloudProvider.edge_hosts — which edge.py already consumes via fnmatch. _match_cloud() (line 160) is 21 sequential if/any() branches with cloud names 'azure'/'gcp' returned at 9 sites. Adding cloud #4 = 80–140 new lines across 2 files, and the two host tables silently drift.

Solution

Promote multi_cloud.py to a thin matcher that reads from the registry. Move path-prefix / query / OData predicates onto CloudProvider metadata (alongside edge_hosts) so each cloud declares its own routing surface. One match(request) → cloud loop replaces the if/elif chain. builtin.py becomes the single source of truth; edge.py and the handler share it.

Benefits

  • Leverage: add cloud #4 in ~4–6 lines of metadata, zero handler edits.
  • Locality: one routing table, no drift between the three definitions.
  • Test surface: routing becomes a pure (host,path,query)→cloud function — table-test every cloud without booting a gateway.

#2 · stack / reset

Push reset + inventory behind a Cloud seam

Strong

Files

  • aws/services/_localstack_stack.py (if/elif ×3 + 9 per-cloud fns)
  • aws/services/internal.py router wiring 778–796
  • azure/gateway.py · gcp/gateway.py own the stores

Problem

The HTTP handler is deep with the wrong stuff. Lines 511, 537, 570 are three if cloud=='aws'/elif 'azure'/elif 'gcp' chains, and the actual reset/inventory logic reaches inside each gateway: gateway.stores._subscriptions for Azure, gateway.stores._projects for GCP, Moto backend walking for AWS. The isolation contract ("reset X never touches Y") holds only by convention — there is no structural boundary. Gateway internals leak across the seam.

Solution

Give every cloud gateway a uniform inventory() → Stack and reset(service=None) → Result. The handler then does registry.require(cloud).build_gateway().reset() — no per-cloud branch. Each gateway owns its own store-walking; the seam is the two methods, not the raw attributes.

Benefits

  • Isolation by construction: a gateway can only touch its own stores — cross-cloud leak becomes impossible, not merely discouraged.
  • Leverage: cloud #4 implements 2 methods; the handler never changes.
  • Test surface: test reset() against an in-memory gateway — no HTTP, no Moto globals.

#3 · stores / spec

Extract BaseServiceSpecRegistry + BaseCloudStores

Strong

Files

  • azure/spec.py ↔ gcp/spec.py register/get/_key word-for-word identical
  • azure/stores.py ↔ gcp/stores.py lazy get_X + CaseInsensitiveDict identical

Problem

AzureServiceSpecRegistry and GcpServiceSpecRegistry are identical except the spec dataclass, one field name (namespace vs service) and the exception class. Same for the stores' lazy get_subscription/get_project and a copy-pasted CaseInsensitiveDict (lines 8–29 in both). Bug fixed in one will not reach the other.

Solution

One generic BaseServiceSpecRegistry[SpecT] (exception + key-fields injected) and one BaseCloudStores[T] with get_scope(id)→ScopeStore[T]. Azure/GCP subclass and alias their domain method. CaseInsensitiveDict lives once.

Benefits

  • Locality: ~120 LOC deleted, validation/exception logic in one place.
  • Deletion test passes: remove the base → identical code reappears in N clouds = it earns its keep.
  • Test surface: register/get edge cases tested once on the base, not per cloud.

#4 · registry contract

Give CloudProvider.metadata a schema

Worth exploring

Files

  • cloud/base.py CloudProvider, list_services()
  • cloud/builtin.py ad-hoc metadata dicts 78–143

Problem

metadata is an untyped dict[str,Any] filled per-cloud with scope_terms / id_format / auth — no schema, so callers introspect keys blind. list_services() (base.py 43–48) hasattr-duck-types and returns {} silently on mismatch. Factory import paths are hardcoded strings; a missing module fails at first request, not at registration.

Solution

Replace the free dict with a typed CloudMetadata dataclass (scope_terms, id_format, auth). Make list_services() raise on an unrecognised registry shape instead of returning {}. Optionally validate factory targets at register_builtins() time.

Benefits

  • Interface honesty: the metadata contract is the type, not tribal knowledge.
  • Fail fast: bad cloud wiring surfaces at boot, not mid-request.

Pairs naturally with #1 — the routing predicates would live on this same typed metadata.

#5 · gateway scaffold

Data-drive gateway provider/router wiring

Worth exploring

Files

  • azure/gateway.py __init__ 105–128
  • gcp/gateway.py __init__ 73–142

Problem

Both __init__ are the same shape: build N providers via X(resource_manager, stores), then N routers via Y(provider=...). GCP: 15 providers + 17 routers; Azure: 4 + 7. The scaffold is identical; only the list differs.

Solution

Declare providers/routers as data ([(attr, ProviderCls), …]) and let a shared loop instantiate + attach. Keep _select_router() per-cloud — Azure regex vs GCP host-equality dispatch is genuinely diverging and a shared base there would just breed overrides.

Benefits

  • Locality: wiring becomes a readable manifest per cloud.
  • Caveat: lower ROI than #3; only the constructor is shared, dispatch stays separate. Defer until a 3rd cloud confirms the pattern.

#6 · console UI

Consolidate *Overview.tsx (blocked by F4)

Speculative

⚠ Contradicts a documented decision. .claude/rules/ui-ux.md §6: "Não refatorar para componentes genéricos multi-cloud até PLAN.md fase F4. Manter padrão de rotas dedicadas." Surfaced for awareness only — do not action before F4.

Finding

aws/azure/gcp/overview.tsx are ~65–75% structurally identical (same useQueries → switch(service.id) → render). Note: the stack.tsx route layer is already deep — AwsStack/AzureStack/GcpStack delegate to one parameterized CloudStack(cloud) with 0% duplication. So the good pattern exists; overview just hasn't adopted it yet.

Post-F4 move

Collapse three overviews into CloudOverview(cloud) driven by registry.ts — ~60–70% reduction, mirroring how CloudStack already works. Also extract the identical azure.ts/gcp.ts fetch error-handler (F4 already permits this one).

Top recommendation

Start with #3 (Base store/spec), then #2 (reset seam), then #1 (routing table)

#3 first — it's the lowest-risk, highest-certainty deepening: pure de-duplication with zero behavioural change, it passes the deletion test cleanly (delete the base → identical code reappears in every cloud), and it establishes a cloud/_base/ home that #1 and #2 then build on.

#2 next — the isolation contract is currently held by convention; turning reset()/inventory() into a gateway seam makes cross-cloud leakage structurally impossible and unblocks adding cloud #4 without touching the HTTP handler. #1 completes the picture: with metadata typed (#4 folds in here), routing collapses from 3 drifting tables into one.

All three share one north star repeated across CLAUDE.md + multi-cloud.md: "adding OCI/cloud #4 = new dir + register, no edits to shared handlers." Today that promise is false in routing, reset, and stores/spec. These three make it true.

None contradict an ADR (none exist). #6 alone is blocked, by ui-ux.md §6 F4. Suggest writing the first ADR to record the "data-driven multi-cloud seam" direction once #2/#3 land.
